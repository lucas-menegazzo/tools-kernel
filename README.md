**The point:** three legacy apps were exported from Power Apps and rebuilt on a shared kernel. A fourth app, deliberately different, was built last to see if the marginal cost really drops.

## TL;DR

- Built a shared PostgreSQL kernel with audit, RLS, PII masking and four-eyes approval.
- Ported three Power Apps from `legacy/` to `apps/`.
- Added a fourth app that the schema did not anticipate.
- The cost curve dropped: the fourth app, intentionally harder, still cost less than the first.

## What it replaces

The legacy Power Apps are in `legacy/`, unpacked from their `.msapp` files. See [`legacy/README.md`](legacy/README.md) for what each one does wrong.

## What I built

I simulated an export of the three legacy apps from Power Apps and a migration to a shared kernel carrying the common and regulated code, then built the three apps from the brief on top of it. Each one is a schema, a permission map, and the logic specific to it. I built this to show Devin is at its most useful as the context layer across a codebase, accumulating all the necessary business logic from code, then operating on its own.

Then I built a fourth app that was not in the brief, built last and deliberately shaped differently, to measure two things: how much faster it went, and how much of it was already decided by the first three.

The apps in `apps/` are:

- `kyc-review-queue` — the first app, ported from `legacy/KYCReviewQueue/`
- `refunds-dashboard` — the second app, ported from `legacy/RefundsDashboard/`
- `feature-flag-admin` — the third app, ported from `legacy/FeatureFlagAdmin/`
- `restrictive-list-screening` — the fourth app, deliberately two-related-entity, not in the brief
- `dispute-review-queue` — the fifth, from a non-engineer issue in Portuguese

Identity, customer data and the bureau connectors are mocked.

## Architecture

```
┌─────────────────────────────────────────────────────┐
│  apps/  →  kyc, refunds, feature-flags, screening,  │
│            dispute-review-queue                     │
├─────────────────────────────────────────────────────┤
│  core/  →  session context, RLS, audit trail,       │
│            PII masking, soft-delete, approvals      │
├─────────────────────────────────────────────────────┤
│  PostgreSQL 15  +  tools_kernel_app (NOBYPASSRLS)   │
└─────────────────────────────────────────────────────┘
```

Apps are a shell layer over a shared kernel (`core/`). The regulatory surface lives in the kernel: auth (SSO), RBAC, audit trail, PII-masking, four-eyes approvals. The kernel also carries the shared UI set and the schema-to-app scaffold. Row-level policies are enforced and forced in the database, and the audit trail is a hash chain, so "how do you know this log was not altered" has an answer.

## How to run it end to end

```bash
git clone https://github.com/lucas-menegazzo/tools-kernel.git
cd tools-kernel
docker-compose up -d
```

The init script in the container loads the kernel and the apps wired into `docker/init-db.sh`. To load or reload any app by hand:

```bash
docker exec tools-kernel-postgres psql -U tools_kernel -d tools_kernel -f /apps/<app>/schema.sql
docker exec tools-kernel-postgres psql -U tools_kernel -d tools_kernel -f /apps/<app>/seed-data.sql
```

Run the checks:

```bash
npm run check
```

Start the dev server:

```bash
npm start
```

Open `http://localhost:3001`.

## How to sign in as different people

The actor selector in the UI sets the PostgreSQL session context. Pick one of the seeded actors and the queue changes.

- **marina.alves@thefintechcompany.com.br** — `Analista Compliance`, Team A. Sees only her KYC cases. Cannot approve.
- **helena.castro@thefintechcompany.com.br** — `Supervisor Compliance`, Team A. Sees all Team A cases. Can approve.
- **juliana.prado@thefintechcompany.com.br** — `Gerente Compliance`, Management. Sees all cases.

The same mechanism applies to the other apps: the database resolves `current_actor_id()`, `current_actor_team()` and `has_role(...)` for every query.

## How to add a new app

Create a directory under `apps/<app-name>/` with:

- `app.yaml` — entities, fields, PII flags, deadlines with basis, RLS policies, business rules and UI requirements
- `schema.sql` — tables, indexes, RLS, triggers, soft-delete and approval-band wiring
- `seed-data.sql` — synthetic data with the right teams and roles

Then load it with the `psql` commands above. Add it to `docker/init-db.sh` if it should be part of the default `docker-compose up` setup.

## What is deliberately not implemented

- **Identity and auth** — actors are mocked in the UI; the database only sees `current_actor_id()`, `current_actor_roles()` and `current_actor_team()`.
- **Customer data** — CPFs and names are deliberately invalid or synthetic. No real customer records are used.
- **Bureau connectors** — external identity, credit and sanctions checks are not wired in.
- **Remaining apps** — only the apps in `apps/` are built. The rest of the legacy estate is left as-is.
